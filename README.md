# Gummy OS

> **A computer you can open. A playground with real boundaries.**

Gummy OS is a browser-delivered personal creative computer where persistent **Actors** can be opened, composed, and connected to executable **Agents** under Human-controlled **Master Control**.

It keeps the familiar computer—Canvas, windows, files, applications, drag-and-drop, and browser-inside-browser—while adding provider-neutral intelligence, permissioned Molds, explicit synchronization, isolated runtimes, quarantined Gummies, Human-owned Gummy Boxes, and durable Receipts.

The canonical personal address is **mygum.my**.

→ compile deterministic preview

Make Production
→ freeze the current revision
→ create immutable Run and Context Envelopes
→ create Work Orders
→ bind the actual Agent/runtime
→ require Mold, Task Lease, Capability Grant, and Human approval
→ execute eligible bounded capabilities
→ import results and native evidence
→ compare or review

A completed Job is not automatically an accepted result. A revision creates a new immutable Run. Production-specific choices do not become Actor memory without a Human-approved proposal.

## Gummy Canvas and Gummy Bar

The **Gummy Canvas** is where Actors, Gummies, Productions, applications, mini-apps, worlds, tools, windows, and generated surfaces appear and combine. Gummy OS is a toolkit and playground, not one forced workflow.

The **Gummy Bar** is the persistent candy-store system surface. Candy icons may represent Glopper, applications, Actors, Gummies, Bowls, Productions, Work Orders, tasks, notifications, and controls.

A candy icon or utility tile is presentation—not a protocol object, application identity, status authority, or permission principal.

## Security posture

Gummy OS does not replace endpoint security, enterprise identity, network controls, disk encryption, secure boot, EDR, MDM, biometrics, passkeys, hardware keys, or kernel protections.

It adds explicit, testable boundaries:

- everyday work remains inside browser-origin or explicit capsule boundaries;
- Work Orders and provider files are untrusted until validated;
- downloads/imports begin quarantined;
- provider credentials remain outside browser code;
- local companions are bounded and authenticated rather than generic execution APIs;
- native access requires an explicit Bridge, Mold, Lease, Grant, and approval;
- source and accepted Assets are immutable;
- Task Leases prevent silent duplicate ownership;
- ambiguous external Jobs are recovered before any resubmission;
- movement, authority, cost, locality, and outcomes are receipted.

The promise is smaller blast radius and explicit authority—not a claim that browser delivery alone makes a system secure.

## Run and verify

Requirements: Node.js 22 or newer.

```bash
npm ci
npm run brand:generate
npm run utility:generate
npm run dev
npm run check
npm run test:unit
npm run test:integration
npm run test:e2e
npm run test:a11y
npm run test:visual
npm run test:acceptance
npm run build
npm run verify
npm run evidence
npm audit --audit-level=moderate
```

Open `http://127.0.0.1:4173`. The development server binds to loopback unless `HOST` is explicitly set.

`npm run verify` is the deterministic local/CI release gate. `npm run test:live` is opt-in and must never replace deterministic acceptance.

Hosted production should set an exact public origin and stable session secret. Provider and connector secrets remain server-side. No provider source/result content, API keys, installation tokens, private keys, or direct personal identifiers belong in normal server logs.
