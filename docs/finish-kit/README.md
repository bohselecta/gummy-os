## Definition of the release being completed

The target is a **founder-ready personal Gummy OS release candidate**, not the completion of every long-horizon social, enterprise, federation, marketplace, or commercial-network idea.

A new user must be able to:

1. open Gummy OS and understand what it is within seconds;
2. begin locally without GitHub, Google Drive, a provider account, or infrastructure setup;
3. create or open a Production;
4. add and configure specialist Actors without accidentally executing anything;
5. inspect the compiled direction, route, cost, locality, privacy, rights, and expected outputs;
6. choose **Make Production** as the sole execution transition;
7. receive truthful progress, results, Returns, linked specialist/Gummy OS Receipts, and limitations;
8. compare and Human-accept useful outputs;
9. close the browser and return to intact state;
10. understand exactly which capabilities are real, simulated, connected, blocked, or unavailable.

## Release operating rules

- No new product ontology unless current code cannot implement an already-accepted behavior.
- No specialist repository is copied wholesale into Gummy OS.
- Gummy OS owns orchestration, authority, Production scope, Gummy records, Returns, and platform Receipts.
- Each specialist retains its product UI, runtime identity, native records, Assets/packages, and specialist Receipts.
- Configuration is deterministic and non-executing.
- **Make Production executes.**
- Human acceptance remains final and role-specific.
- A deterministic simulator may remain as a demo/test route, but it must never be presented as real provider output.
- Missing external capability creates a useful, exact unavailable state rather than a fake success or global release stop.
- No provider secret enters browser JavaScript.
- No source Gummy or accepted specialist Asset is overwritten.
- The computer tests the computer. Hayden is not the regression harness.
