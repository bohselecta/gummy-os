# Risks, Stop Rules, and Deferred Scope

## Why this document exists

The greatest remaining risk is not that Gummy OS lacks ideas. It is that a final implementation turn could:

- reopen accepted architecture;
- mistake a proposal for completion;
- flatten specialist products;
- create competing branches;
- overfit to the Ranch Day fixture;
- fake live capability;
- or expand into long-horizon scope before the personal release is usable.

This document tells Codex when to keep moving, when to stop one lane, and what is explicitly preserved for later.

## Decision hierarchy

When instructions or implementation choices conflict, use this order:

1. Human authority, consent, rights, law, safety, and data preservation;
2. this finish-up kit and current founder authorization;
3. accepted product/brand/specialist contracts;
4. current canonical code and migration compatibility;
5. automated acceptance and truthful evidence;
6. older active plans;
7. historical receipts, proposals, and implementation preferences.

A lower item may explain history. It cannot silently override a higher item.

## Program risk register

### R1 — Architecture churn

**Risk:** Codex invents new objects, rewrites the shell, or reframes Gummy OS as a generic assistant/project manager while trying to “clean it up.”

**Mitigation:**

- no new ontology without a demonstrated inability to implement accepted behavior;
- prefer additive schema versions and adapters;
- preserve the product map and application identities;
- classify new ideas as release requirement, deferred enhancement, or rejected drift;
- run product-preservation tests in every Gummy OS phase.

**Hard stop:** a change would remove or fundamentally redefine a protected pillar.

### R2 — Plan paralysis

**Risk:** Codex produces another excellent audit or contract proposal and stops before implementation.

**Mitigation:**

- this kit explicitly authorizes implementation through all phases;
- contract reconciliation is the first implementation step, not a conversational gate;
- checkpoint commits replace review pauses;
- continue automatically after every successful phase gate.

**Hard stop:** only an irreversible founder decision remains and no accepted canon or preservation-first default resolves it.

### R3 — False completion

**Risk:** a simulator, stub, capability detector, deployment status, or compiled UI is described as real execution.

**Mitigation:**

- `simulation: true/false` or equivalent evidence;
- separate capability-ready and live-proven status;
- exact provider/runtime Job IDs and output hashes;
- live claims require live smoke evidence;
- unavailable states remain useful and visible.

**Hard stop:** code or copy cannot distinguish simulated and genuine output.

### R4 — Cross-repository contract mismatch

**Risk:** Gummy OS integrates a type/version that does not exist on the referenced specialist head, or a specialist change breaks old fixtures.

**Mitigation:**

- additive native contracts first;
- exact dependency head in Gummy OS fixtures/manifest;
- old and new fixture roundtrips;
- explicit migration adapters;
- update registry protocol status only after compatibility passes.

**Hard stop:** integration requires guessing an uncommitted specialist contract or destructively rewriting history.

### R5 — Branch and PR chaos

**Risk:** multiple Agents create competing build lanes, previews, and “canonical” branches.

**Mitigation:**

- one final release branch per touched repository;
- one final PR per repository;
- checkpoint commits within the branch;
- exact head and dependency mapping;
- classify and close/supersede competing release PRs only after their useful work is preserved;
- one canonical preview per final Gummy OS candidate.

**Hard stop:** working trees/branches contain unrelated unreviewed changes whose ownership cannot be determined safely.

### R6 — Fixture overfitting

**Risk:** Ranch Day-specific names, people, permissions, or sequence assumptions become the product model.

**Mitigation:**

- replace the default visible Production with blank + neutral Night Gummy Launch choices;
- keep Ranch Day only as a regression fixture where valuable;
- add at least two materially different Production fixtures;
- test optional actors, missing specialists, alternate order, and non-video deliverables;
- ensure schemas and UI use generic Production IDs/data.

**Hard stop:** a generic user journey cannot complete without fixture-specific IDs or private relationships.

### R7 — User-facing implementation jargon

**Risk:** a new user sees schema-shaped forms, repository names, raw IDs, GitHub App setup, or infrastructure terminology before understanding the task.

**Mitigation:**

- progressive disclosure;
- product-native specialist surfaces;
- plain-language primary copy;
- technical details remain inspectable;
- content extraction/audit;
- no external account required to start.

**Hard stop:** normal first-run requires developer configuration.

### R8 — Data loss or destructive migration

**Risk:** new schemas, adapter states, backup logic, or identity migration overwrite existing Productions, Assets, or Receipts.

**Mitigation:**

- deterministic idempotent migrations;
- inspect-first import;
- atomic/staged writes;
- preserve divergent versions;
- backup before authority change;
- old fixtures and interrupted migration tests;
- rollback/read-only mode.

**Hard stop:** migration cannot preserve or unambiguously report current data.

### R9 — Identity collapse and authority leakage

**Risk:** Actor becomes Agent, application becomes authority, configuration starts execution, or connected provider gains ambient access.

**Mitigation:**

- enforce Human → Master Control → Mold → Lease → Grant;
- configuration-no-execution tests;
- scope/expiry/revocation tests;
- explicit executor/locality/provider disclosure;
- external provider roots and local companion capabilities are bounded;
- Work Orders remain proposals.

**Hard stop:** consequential execution can occur without the complete authority intersection.

### R10 — Receipt flattening

**Risk:** specialist evidence is copied into a Gummy OS Receipt and the native Receipt/Job/package is lost.

**Mitigation:**

- linked Receipt wrapper;
- immutable specialist IDs/hashes/protocol versions;
- native evidence remains inspectable/exportable;
- integration tests validate both layers.

**Hard stop:** platform integration requires discarding specialist-native evidence.

### R11 — Local companion attack surface

**Risk:** ImageHoss/Meshmallow bridge exposes arbitrary workflows, files, commands, paths, origins, or long-lived credentials.

**Mitigation:**

- loopback-only default;
- ephemeral authenticated session;
- strict origin allowlist;
- bounded schemas/message sizes;
- named operations/workflow allowlist;
- browser cannot choose arbitrary project root;
- no shell or arbitrary Python;
- capability discovery is sanitized;
- adversarial tests.

**Hard stop:** the integration widens into a generic local execution API.

### R12 — Provider cost and duplicate execution

**Risk:** VideoBoss or another cloud adapter overspends, retries ambiguous calls, or loses provider Job ownership.

**Mitigation:**

- server-side broker;
- current cost table and ceiling;
- idempotency keys;
- provider request/Job IDs;
- recovery-before-resubmit;
- no silent retries on ambiguous consequential calls;
- cancellation where supported;
- cost and limitations in Receipts.

**Hard stop:** cost cannot be conservatively bounded or ambiguous calls cannot be recovered safely.

### R13 — External blocker halts the whole program

**Risk:** missing provider key, ComfyUI, Blender, OS feature, or deployment credential causes Codex to stop all work.

**Mitigation:**

- classify the specific live route BLOCKED or NOT CLAIMED;
- finish adapter code, deterministic tests, unavailable UI, docs, and live-smoke command;
- continue every unaffected phase;
- preserve exact blocker in final Return.

**Hard stop:** only the affected live lane stops. The overall turn continues unless the blocker prevents the deterministic personal release itself.

### R14 — Brand dilution

**Risk:** polishing introduces new colors, recolors mascots, makes utility tiles app identities, or blurs Gummy/Glopper roles.

**Mitigation:**

- exact five source colors;
- production asset hash checks;
- Gummy purple-dominant, Glopper gold-dominant;
- utility tiles remain operation mnemonics;
- visual regression in Night and Day;
- no theme marketplace/accent picker.

**Hard stop:** accessibility cannot be achieved within the palette without component restructuring; restructure rather than adding a hue.

### R15 — Giant untestable integration

**Risk:** one big Codex turn becomes one unreviewable commit with no checkpoints or rollback.

**Mitigation:**

- one sustained turn, but sequential phase commits;
- test and evidence gate after each phase;
- one branch per repository;
- final PR summarizes full diff and checkpoints;
- never combine unrelated deferred work.

**Hard stop:** a phase cannot be isolated enough to test or roll back safely.

### R16 — Performance and reliability regressions hidden by feature success

**Risk:** the product technically works but becomes slow, memory-heavy, fragile, or unusable on phone/tablet.

**Mitigation:**

- baseline and final measurements;
- realistic Production fixture;
- viewport matrix;
- refresh/offline/quota/restart chaos paths;
- no infinite spinners;
- optimize measured bottlenecks only.

**Hard stop:** critical first-run or golden-path responsiveness is materially degraded without an accepted tradeoff.

## Global hard-stop conditions

Stop the affected mutation and return exact evidence when:

- a source or accepted Asset would be overwritten;
- migration may discard or ambiguously merge state;
- Actor and Agent would collapse;
- Human approval, Mold, Lease, or Grant would be bypassed;
- configuration would execute;
- a Work Order or application would grant itself authority;
- a provider secret would enter browser code, log, backup, fixture, or Receipt;
- a local bridge would expose arbitrary filesystem, workflow, Python, shell, or device access;
- a provider call may be duplicated unsafely;
- cost/rights/locality cannot be stated before execution;
- a live result cannot be distinguished from a simulation;
- specialist evidence would be flattened or destroyed;
- a public Meshmallow rename would break historical 3D Bee IDs/evidence;
- accessibility or security is being “fixed” by disabling the test;
- a competing branch contains possibly valuable unmerged work that has not been reconciled;
- a release claim exceeds executable evidence.

A hard stop does not authorize abandoning unaffected phases.

## Continue-with-limitation conditions

Continue the program and record the limitation when:

- a real provider credential is absent;
- supported ComfyUI or Blender is absent on the current machine;
- an optional external Box connector is unavailable;
- Gummy Rooms runtime is not connected;
- managed cross-device sync is not ready;
- a long-horizon social/enterprise feature is not implemented;
- wallpaper/Underground final art is not selected;
- a noncritical optional browser/runtime has a documented limitation while required release browsers pass.

The UI must expose the same truth.

## Explicitly deferred product scope

The following remains part of the protected vision but is not required for the founder-ready personal release candidate.

### Broad Social Layer

- public discovery and verified public `@addresses`;
- follows, memberships, broad sharing, public Bowls, Grabs at network scale;
- abuse/moderation systems;
- public-figure and licensed-character systems;
- social ranking/feeds.

Preserve schemas/product visibility where already accepted. Do not let it delay the personal Production loop.

### Gummy Rooms live runtime

- authenticated room service;
- production multiplayer/social presence;
- large-scale fair queues and live mirrors;
- public/remote collaboration.

Keep the application visible and truthfully unavailable until connected.

### Enterprise Habitat

- organization administration;
- OIDC/SAML/SCIM;
- EDR/MDM/SIEM integration;
- policy registries/runtime pools;
- compliance packages and enterprise retention;
- sovereign/dedicated deployment modes.

Do not remove the architecture. Do not build it into this personal release.

### Federation and portable network life

- signed federated discovery;
- multi-server Bowls/Gummies/Links/Grabs;
- independent edition compatibility;
- key rotation across federation;
- certification network.

### Billing, marketplace, and commercial network

- subscription billing;
- model credit marketplace;
- paid Application Packs;
- provider marketplace;
- certification/support commerce.

A Cost Shield and truthful cost evidence are required now. A marketplace is not.

### Broad native OS bridge

- generic device control;
- unrestricted shell/filesystem/process APIs;
- ambient synchronization with the native distro;
- rebuilding the existing AI-native Linux distribution;
- general desktop automation beyond separately accepted bounded capabilities.

Only narrow deny-by-default specialist/native bridges belong in the release.

### Managed Gummy Box and all connectors

A polished managed Box, GitHub connector, and Drive connector are valuable. The founder-ready local release requires Local Box, backup/restore, and connector-safe architecture—not every external provider.

### Multiple creative provider expansion

One proven route per specialist is enough to establish the adapter. Do not widen to many image/video/3D providers before the first route and recovery semantics are solid.

### Full video editor or game engine

VideoBoss is not required to become a complete nonlinear editor. Meshmallow is not required to become a game engine or finished-game generator.

### Physical realization and manufacturing

The open `bohselecta/3d-bee` physical-realization handoff remains a separate future lane. Gummy OS/Meshmallow may preserve a typed seam, but this release does not claim engineering, DFM, quoting, procurement, compliance, safety, or manufacturability.

### Wallpaper and exact Underground art

Final wallpapers and exact Underground art direction are founder-facing visual polish. They may be added after release gates pass. They cannot block functional completion or dictate a new shell architecture.

### Standalone native/mobile Glopper applications

Preserve the identities and interfaces. The release may remain browser/PWA-first with separately governed executors.

## Rejected drift

Do not implement these as “helpful simplifications”:

- replace Gummy OS with a single chat screen;
- turn Production into a generic project/task list;
- treat specialist applications as prompt textareas;
- make GitHub the user’s required storage/backend;
- merge ImageHoss, VideoBoss, or Meshmallow code wholesale into Gummy OS;
- make all service Actors one generic Agent;
- remove Receipts or hide executor/provider identity;
- auto-run when an Actor is added or configured;
- auto-promote Production choices into personal Actor memory;
- add new brand hues/themes;
- rename historical 3D Bee identities destructively;
- claim local/browser hosting is automatically secure;
- skip or weaken tests to produce a green build;
- ask Hayden to perform routine regression testing.

## Final scope test

Before accepting any work item, ask:

```text
Does this make the personal Gummy OS release easier to understand,
safer to operate,
more truthful,
more durable,
or complete a required Production journey?
```

If not, preserve it in deferred scope and finish the release first.
